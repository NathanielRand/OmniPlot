Org / Shop / Team Overhaul — Plan

Current state (confirmed): flat two-tier model, no org entity. User 0..1 — 1 Shop, Shop 1 — many ShopMember, roles hardcoded as ShopRole = owner|manager|tech. Everything is Firestore client-SDK + firestore.rules, no server-side membership API. shopId/shopRole scalars on the user doc are read/written at 116 call sites across the app (settings page, join flow, admin panel, billing) — this rules out a rewrite; the migration must be additive.

Target model

- Organization (new, top of hierarchy): the paying entity. id, name, ownerId, plan, seats, stripeCustomerId, ... — effectively what Shop billing fields are today, moved up one level.
- Shop: becomes orgId-scoped, drops billing fields (now just a location/site record).
- Team: org-level group (not per-shop, not a shop subdivision) whose role grant is scoped to one or more shops, or org-wide. This is the plain reading of "an org having multiple shops and multiple groups of teams" and it's the only shape that keeps permission resolution to one document read (see below) — not attempted as "teams nested in shops."
- Membership doc: orgs/{orgId}/members/{uid} — the single source of truth, holding the resolved permission set + which shopIds it applies to. This is the doc Firestore rules and server routes actually read. Firestore's rules-evaluation budget doesn't support walking org→team→role→permission chains per request, so nothing in rules ever traverses that chain — it's precomputed into this one doc whenever a role/team assignment changes.

Why additive, not a rewrite

Keep shopId/shopRole on the user doc as a "default/last-active shop" UI pointer — every existing consumer (shopStore, settings page, handlePortal("shop"), the join page's shopId equality check, admin's removeShop action) keeps compiling. The membership doc becomes authoritative; the scalar becomes a convenience cache updated alongside it.

The privilege-escalation gap that has to close first

firestore.rules:131–136 lets any signed-in user update a shopInvite doc (that's how accept works today) and reads on it are public. With only 3 shop roles the blast radius is small. Once invites can carry cross-shop/team grants, that same permissive rule lets a user rewrite the invite's role field before accepting themselves in. Rules can't express "can't grant a permission you don't hold," "can't self-escalate," "last owner can't be removed," or org-wide seat limits. So: all membership/role/invite/team mutations move to +server.ts routes using the Admin SDK; Firestore rules become a deny-by-default backstop, not the authorization layer. This is implied by the request but not stated, and is the piece most likely to get under-scoped if skipped.

Billing must be explicitly rescoped, not deferred

stripe-ledger.ts keys everything on metadata.type: 'shop' + shopId, and writes subscription status onto shops/{shopId}. If the org becomes the payer: new metadata shape, a new webhook branch, SHOP_PLAN_LIMITS/SHOP_PRICING_PLANS rekeyed to org, seats reinterpreted as an org-wide pool instead of per-shop — and existing live shop subscriptions need a migration or a compat branch reading either metadata shape. This is the item most likely to break silently in production if left implicit.

Phasing (each phase ships independently)

1. Org entity + membership docs, additive. Add Organization, OrgMember types; backfill one org per existing shop (org.ownerId = shop.ownerId); keep shopId/shopRole scalars working unchanged.
2. Server-side membership/invite/role routes + tightened rules. Move mutations off client SDK; rules become read-mostly + deny-by-default writes.
3. Teams: org-level team entity, scoped grants (shop subset or org-wide), permission resolution written into the OrgMember doc on any change.
4. Billing rescope: org-level Stripe customer/subscription, metadata migration for existing shops, seat semantics.
5. UI: org switcher, shop switcher, team management screens; settings page's "team" tab splits into shop and team management.

todo.txt is currently modified on dev — flagging since it's uncommitted local state, not touched by this plan.
